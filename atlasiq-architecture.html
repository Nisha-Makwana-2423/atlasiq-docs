01Executive Architecture Summary

AtlasIQ is designed as one shared application codebase operating within Constellation's protected Azure environment. Customer data is separated from intake through processing and storage. The application resolves trusted tenant, customer and program context for each request and routes it to the correct customer-specific resources.

Architecture areaDecision / design baseline

Platform control planeOne central Platform Control Database holding minimum tenant/customer directory and routing metadata; no customer PHI or operational records.

02Logical Architecture Overview

03Architecture Layers and Responsibilities

LAYER 1Platform Control Database · central directory and routing, no customer data
LAYER 2Tenant Customer Master Database · one per tenant, configuration and customer registry
LAYER 3Customer Workspace + Dedicated Database · one per customer, own encryption key

3.1 Layer 1: Platform Control Plane

The Platform Control Database is the central directory for the AtlasIQ platform. Its purpose is platform-level visibility, tenant/customer discovery and routing, not storage of tenant or customer operational data.

  • Tenant identity: tenant ID, display name and lifecycle status.
  • Customer directory metadata: customer ID/name and tenant association, as needed for platform-level discovery.
  • Resource references: identifiers or secure references for tenant/customer databases and their associated Key Vault resources.
  • Routing metadata: the information required by the application to resolve the correct tenant and customer resources.
  • Provisioning and lifecycle status required for platform administration and support.
Data boundary

No customer PHI, documents, claims, provider records, case records or other customer operational data is stored in the central Platform Control Database.

3.2 Layer 2: Tenant Customer Master Database

Each tenant has a separate Tenant Customer Master Database. It stores configuration belonging to that tenant and the tenant's customer master/registry information. It is not a shared database across tenants and it does not replace the dedicated database for each customer.

  • Tenant-specific configuration: contracts, programs, service types, roles and permissions, queues, clocks and workflows (examples explicitly listed by Paul).
  • Customer master records and customer-to-resource references, including references to each customer's dedicated database and encryption key.
  • Tenant administration configuration and operational settings required to configure customer workspaces.
  • Tenant-specific schema/version metadata and configuration history as required by the design.
Terminology

Tenant Customer Master Database is the working name used in the architecture. It describes the per-tenant store for tenant configuration and customer master/registry information.

3.3 Layer 3: Customer Workspace and Dedicated Database

Layer 3 is a customer workspace, not a customer-run AtlasIQ administration layer. Constellation's tenant administrators configure each customer. Customer staff sign in through the customer's identity provider and receive limited portal access.

  • Each customer has its own dedicated database. This is an explicit initial requirement and part of the approved database architecture.
  • Each customer has a separate customer encryption key, managed in Azure Key Vault; the application stores/uses a secure key reference rather than plaintext key material.
  • Customer operational records, documents/metadata, provider records, case/claim data and customer-specific application data remain within that customer's data boundary.
  • Customer-specific configuration and authorized access are applied to the relevant workspace.
  • Customer database and key are designed to support independent export or handover, subject to the agreed contractual and key-transfer procedure.

3.4 Shared Application Layer

AtlasIQ uses one shared codebase for all customers. The application must not rely on separate application deployments or code forks to achieve data isolation. Isolation is enforced through trusted request context, authorization, resource routing and customer-specific processing resources.

04Request and Data Processing Architecture

4.1 Request resolution and routing

  1. User or external source submits a request through an authenticated channel associated with a customer.
  2. The platform authenticates the caller or validates the source integration and resolves the trusted tenant, customer and program context.
  3. Authorization checks validate the user's role, tenant boundary, customer workspace, program and requested action.
  4. The application selects the customer's configured intake pipeline, queue, worker, search index and database using approved routing metadata.
  5. Processing uses only the selected customer's data, policy library and permitted resources.
  6. Results and audit events are written to the correct customer resources. Any unmatched or ambiguous source/customer association is quarantined for review.

4.2 Customer-specific processing pipeline

  • Intake: customer-owned channels and credentials, including configured SFTP/API feeds and portal/document uploads.
  • Validation: malware/content checks and validation that the source channel matches the intended customer. PHI screening is included where required by the approved security design and workflow.
  • Processing: customer-specific queues, workers and search indexes. AI-assisted processing is bounded to the customer context.
  • Quarantine: records that cannot be reliably associated with a customer are held for review and are never routed by guesswork.

4.3 Search and AI context isolation

  • Search/retrieval is filtered to the relevant customer's search index and authorized content.
  • Each AI request is constructed from the relevant customer's data and policy library only.
  • No cross-customer retrieval, memory or context reuse is permitted.
  • Private AI gateway is the architecture component name. The exact production model/runtime, capacity, evaluation thresholds and fallback behavior remain subject to the AI/security decisions listed in the requirements inventory.
  • AI output that supports claims, clinical or operational work must preserve evidence lineage and remain subject to human review where required by the approved workflow.

09Database Schema Evolution and Release Architecture

Paul's confirmed direction is that production schema migrations are version-controlled and executed through the deployment pipeline, never as ad hoc manual production work.

  • Maintain a schema-version table in every customer database. Tenant configuration databases must also have a controlled schema-version strategy.
  • Use a controlled, batched rollout across customer databases, with post-migration validation.
  • Automatically halt the rollout on the first failure; do not continue to later databases until the failure is investigated and resolved.
  • Provide a versions/status dashboard so platform/managed-services teams can see the current and target schema version and migration outcome per database.
  • Managed services monitors migration outcomes and owns operational resolution under the Managed Services agreement.
  • Migration design must account for compatibility between the shared application release and databases that may temporarily be on different schema versions during a batch rollout.

This section records the architecture and release decision only. Detailed execution steps, alert procedures, recovery commands and operational ownership checklists belong in a separate operations runbook.

10Isolation, Portability and Handover Architecture

  • Customer-level isolation is enforced across database, encryption key, intake channels, queues, workers and search index.
  • Automated customer-isolation tests run on every release. Synthetic canary records must never cross customer boundaries; cross-customer access attempts are blocked, logged and alerted, as stated in Paul's Option A architecture.
  • A customer's database can be exported or handed back at contract end without touching another customer's data.
  • Customer handover must consider the database, associated document/object storage, customer-specific configuration, audit history, schema/version information and encryption-key custody together.
  • Key handover must be planned with data handover. Depending on the receiving environment and key-management model, the key may be transferred securely or the data may be re-encrypted under a recipient-controlled key before old access is revoked.
  • Tenant-level handover includes the Tenant Customer Master Database and tenant-specific configuration. Customer-level portability remains independently supported by the dedicated customer database boundary.
Handover acceptance principle

The receiving party must be able to restore and read the transferred customer data and associated documents using transferred or re-established key material, without access to another customer's resources.

11Deployment, Hosting and Operational Architecture

  • Option A identifies Constellation's own Azure subscription and US East as the hosting boundary/region. Final subscription, environment and region details must be confirmed during deployment design.
  • Private networking, WAF, managed identities/service identities, least privilege, encrypted storage and centralized audit/monitoring are foundational platform controls.
  • Tenant creation in Milestone 2 is performed by scripts and infrastructure-as-code through the deployment pipeline; there is no Super Admin tenant-onboarding UI in Milestone 2. One tenant is planned at launch (SOW §18.1); expanded tenant self-administration is excluded under SOW §16.5.
  • Constellation requests customer onboarding. A simple request form in the tenant admin screen may capture the request, but fully self-service UI-triggered automated customer onboarding is excluded from the MVP under SOW §16.5.
  • The owned automated provisioning pipeline creates the customer database and Key Vault key, applies schema, registers resources, validates and activates; failure handling includes rollback/cleanup and alerts.
  • Managed services monitors platform health, provisioning and migrations and resolves operational failures under the Managed Services agreement.
  • Architecture requires observability for application, integration, queue/worker, database, security and AI services. Exact tooling, SLOs, support hours and alert thresholds remain to be confirmed.
